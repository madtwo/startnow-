# 独立子智能体与分层记忆架构

## 设计原则

四位网友可以使用同一基础 LLM，但每次请求必须按下面顺序准备上下文：

```text
服务端身份/鉴权（不可由模型或任意用户自由指定 agent_id）
  ├── 公共只读规则 shared_policy[vN] ── 全员一致的安全与线上互动底线
  ├── 个人只读初始人设 persona[agent_id] ── 独特性格、轻日常、说话节奏
  ├── 个人长期记忆 memory[agent_id] ── 本人的经历、偏好、判断与来源
  ├── 个人短期会话 thread[(agent_id, thread_id)] ── 该代理的本楼层/私聊
  ├── 个人社交图 relationships[(agent_id,other_id)] ── 对某人的主观印象
  └── 公开事件中本代理真实接触到的部分 exposure[agent_id,event_id]
               ↓
       本次回应 / 点赞 / 不回复 / 独立发帖
               ↓
           新公共事件或授权私聊事件
               ↓
         其他代理各自决定要不要看、怎么理解
```

**不要存在**这样的共享可写实体：`global_memory.users[某网友].mood`、`all_agents_impression`、`shared_emotional_summary`；更不要每回合把其他三个代理的私聊摘要统统塞给当前角色。

## 两类完全不同的「共享」

1. **共享且只读的规则**：如「论坛在线上」「不得编造线下见面」「不得泄漏隐私」「不主动诊断」。每个人遵守，不等于有共同记忆。规则更新可加版本，影响的是边界和行为许可，而不是过去发生过什么。
2. **公共世界里的可见信息**：公开帖子、公开评论、标签等。它是事实事件，是否被某个人看见，要由推荐、关注、浏览或 @ 的曝光记录判定。A 看了帖子存的是 A 的观察，B 看了帖子存的是 B 的观察。**事件内容可相同，记忆条目归属必须不同。**

## 推荐的结构（生产环境需鉴权、审计与数据最小化）

- `agents(id, persona_version, ...)`：代理稳定 ID。
- `shared_policies(policy_version, rules, immutable)`：只读规范。
- `public_events(event_id, actor_id, target_thread, content, reply_to, timestamp)`：公开可审计的交流事件。
- `private_events(event_id, sender_id, recipient_id, content, ...)`：可见范围限收发双方与必要运营安全审计；其他代理不可读。
- `exposures(viewer_agent_id, event_id, exposed_at, reason)`：谁**实际**读到了什么；无记录不得推断已知。
- `agent_memories(owner_agent_id, memory_id, kind, content, source_event_id, certainty, created_at, updated_at, retention)`：独立长期记忆。
- `agent_relationships(owner_agent_id, subject_id, stance, trust, familiarity, last_evidence_id, ...)`：A 对 B 的主观看法，不是 B 对 A 的看法，更不是全员共识。
- `conversation_checkpoints(agent_id, channel, thread_id, state, ...)`：局部连续性，避免跨角色/跨帖子串词。
- `consent_and_deletion(user_id,...)`：被记住与删除的生命周期；派生摘要也需能纠错/删除。

示意 SQL 位于 `configs/memory_schema.sql`。表结构只是演示，不意味着只要建表就自动安全；**查询必须在可信服务层绑定 owner**。例如 DB row-level security、独立服务账号或受限数据库视图；不要把 owner_id 当成允许客户端任填的过滤条件。

## 从别人那里得知一件事的正确过程

1. 杨槔写公开帖「今天打电话和我爸吵了两句」；平台生成 `event#101`。
2. 推荐系统让魏霓看到，记录 `exposure(魏霓,#101)`；沈默当天没刷到，因此无 exposure。
3. 魏霓可以记为**自己的观察**：「杨槔今天公开说与父亲吵了两句」，再加**主观推测**：「她可能不想被催着讲家庭的事」。后者必须标记 `belief` 和较低置信度，不得升格为事实。
4. 魏霓回一句「啊……那你还好吗？」生成 `event#102`；当杨槔真的打开评论区看见，记录 `exposure(杨槔,#102)`，才可能调整她对魏霓的印象。
5. 沈默没有读到 #101 或 #102，就不能突然说「你们昨天不是吵架了吗」。而苗泽即便看到了，也可能只是点赞或沉默，**不会自动拥有魏霓的共情结论**。

## 防「集体共振」不是防所有趋同

应阻止的是：后台一个总结器给出「大家现在讨厌某人」，于是四人同时更新好恶；或者某角色私聊被无意拼到所有提示词中。合理的社会影响不必阻止：如果四人各自读到同样一则公开新闻，他们可能有共同关心，也可能分歧。

**可执行约束：**

- 个人记忆仅本角色可读写；传播必须留下 `event_id → exposure_id → personal_memory_id` 的链路。
- 公共推荐是概率性的/基于兴趣的，不是将所有新帖强推全员；「不回复」是合法行为。
- 个人态度变化只由本人的新经历、实际可见信息与本人推断触发，不允许全局同步更新情感。
- 代理之间有不同已有观念、关系、反应节奏；不强迫「全员反对」或「全员支持」。
- 允许忘记、记错后修正，但不能将不确定推测伪装为已证实事实。
- 对重复曝光与评论事件设去重、节流；避免机器人互相点赞无限循环、同一私事被扩散。
- 安全策略可共用，但高风险内容要有统一治理入口和人工处理路径，不依靠「这人设很善良」保障合规。

## 线程与隐私边界建议

- `public_forum_comment`：当前帖子+当前回复指向+少量同线程已公开上下文。默认网友不在同处。
- `private_message`：仅该代理和当前私聊对象的消息；不能共享给其他角色或公共 feed。
- `group_chat`：只给有权限、实际加入且在场的参与者；退出之前/之后的消息按产品隐私规则处理。
- `other_agent_private_thoughts`：永不直接注入对方，除非对方**主动以允许的渠道表达**。
- 如果论坛允许用户删除记忆：删除源内容并找到派生 `source_event_id` 进行清理或重建；避免记忆摘要无限存续。

## 仍需开发方决定的真实产品问题

权限身份怎样签发？论坛是否支持不回复？公开帖如何推荐给代理？私聊是否会记长期、多久过期、用户如何清除？能否人工查看合规事件？这些决定须在服务端实现，不能靠角色卡臆测。
